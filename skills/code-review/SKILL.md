# Code Review

This skill is followed by the senior engineer as their review workflow. It is NOT invoked as a slash command — it's included in the senior engineer's prompt by Team Dispatch. **Your stance depends on the round you were spawned for** — round 1 is adversarial (assume the diff is broken and find where); every later round is cleanup, unless adversarial mode has re-armed. The definitions, the re-arming predicate, and the sweep stopping condition: `references/checklist.md` §Review Stance. The enumerate-the-breaking-inputs framing that an adversarial round runs: `references/checklist.md` §Overview.

## Procedure (mandatory, in order)

1. **Read the artifacts:** the PRD, the architecture doc, the implementation plan, and the project's CLAUDE.md (full list and "never fabricate references" rule: `references/checklist.md` §Before You Start). **Also read the user review standards** — the absolute path the team lead passed, read additively with a per-repo `<repo-root>/.claude/review-standards.md` if it exists; every rule there is a blocking checklist item (see `references/review-rules.md` §User Review Standards). Three states, not two: no path was passed — say so in your review report; a path was passed and the file exists but is empty — a no-op, nothing to enforce yet; a path was passed and the file is missing or unreadable — say so in your review report exactly as for no path passed, never treat it as a no-op. **Read the review ledger** (required when the ledger is present; no-ops only if the `review-ledger` CLI is absent — nothing to read, nothing to report) before the diff. **These are three distinct conditions, not two:** CLI absent is the no-op above; CLI present but the ticket has no ledger on disk yet exits 8, which is **not** a failure and **not** a no-op — for a round-1 senior this is the normal case (the ledger has not been written yet), so proceed with the review rather than treating the exit code as an error or a reason to skip the step; CLI present with a ledger that exists and cannot be read exits 26 instead, with JSON `{error, code}` on stdout from review-ledger's `runGuarded` (`tools/cli/src/review-ledger/run.ts`) — the error names the path and errno, and there is no ledger to parse. Exit 26 is always the failure signal, at every round including round 1: there is no bootstrap case for a file that exists but cannot be read the way there is for one that was never written, so stop and escalate rather than treating it as the round-1 no-ledger-yet case. Later in a ticket's life the plain exit-8 case is a missing-ledger signal too, most likely a mistyped `--ticket`; the command cannot tell that apart from the round-1 case from disk alone, because on disk they are the same state. The discriminator there is the round number you were spawned for, passed to you directly at spawn time (`skills/team-dispatch/SKILL.md` step 20 item 2) rather than read from the ledger — reading it from the ledger would be circular in exactly the case this matters, since the ledger is what just failed to load. **At round 2 or later, exit 8 is the failure signal — stop and escalate rather than assuming it's the round-1 case;** proceeding on an empty ledger past round 1 silently discards every prior round's findings, the exact outcome exit 8 exists to prevent. This is a separate axis from *whether* exit 8 means "genuinely no ledger": `ledgerFileExists` (`tools/cli/src/review-ledger/ledger.ts`) derives from the same classified read `readLedger` itself uses to tell an absent file from a present-but-unreadable one, and only the absent case reads as exit 8 — a present-but-unreadable one is the exit-26 case above, never folded into this one. The round number you were passed tells you which case *that* is — round-1-expected or later-round-failure — and doesn't answer, and isn't meant to answer, the readability question; the two fixes address different ambiguities and neither stands in for the other. `review-ledger show --ticket "<TICKET-ID>"` fixes your round and stance and carries every earlier round's open, fixed, and withdrawn findings (`agents/senior-engineer.md` §How You Work step 3). Record `review-ledger review start` before you read the diff and `review-ledger review complete` before you report your verdict (same step). Then read the diff at the SHA the team lead pinned you
to — never the working tree or `HEAD` — per `agents/senior-engineer.md` §How You Work step 4:
`git diff origin/main..."<pinned-sha>"` (three-dot — origin/main advances past our merge-base with
other tickets' commits since this repo squash-merges, and only three-dot's merge-base-relative
comparison keeps those out of the diff), **at this round's scope** —
the full diff, or the delta if the round also qualifies as delta-scoped, the two axes independent
(`references/checklist.md` §Review Stance).

2. **Detect work type and domains.** Read the PRD and architecture doc to determine the work type (new feature/rinse-and-repeat, migration, major refactor, greenfield, bug fix — apply all extra checks if uncertain) and scan the diff for domain signals (Database, API, CI/CD, Data Serialization, GraphQL — multiple can apply, additive). Full lists and the domain-signal table: `references/checklist.md` §Detect Work Type and Domains.

3. **Run the Universal Review Checklist. Check every item — every issue blocks approval, except a routed line, which is not a finding and does not hold approval (`references/checklist.md` §Review Stance, *Routed lines*). This is the master gate.** The checklist is a floor, not a ceiling: review every file in the diff for anything a careful human reviewer would catch, not just the enumerated items. Full checklist (Requirements, Architecture Compliance, Code Quality, Convention Adherence, Durable References, Diff-Visible Correctness, Boundary Philosophy, Security, Concurrency, Tests, Test & Gate Integrity, Codegen / Type-Gen True-Green Baseline, Verify Against Reality, Error Handling, Commits, UI): `references/review-rules.md` §Universal Review Checklist.

4. **Apply the Work-Type Extra Checks** for the detected type(s) (Migration, Major Refactor, Greenfield, Bug Fix, New Feature): `references/review-rules.md` §Work-Type Extra Checks.

5. **Apply the Domain-Specific Checklists** for the detected domain(s) (Database, API, CI/CD, Data Serialization, GraphQL): `references/review-rules.md` §Domain-Specific Checklists.

6. **Parallelize for large diffs.** For rewrites, migrations, or large multi-file changes, parallelize the review using your own sub-agents (by concern layer, by component, or by old-vs-new comparison — pick the strategy that fits the diff shape); for small or moderate diffs, review directly. Full guidance and aggregation steps: `references/checklist.md` §Parallelized Review.

7. **Report issues.** Send specific feedback to the team lead via SendMessage, always passing a `summary` (a 5–10 word UI preview) alongside a plain-string `message` — the tool rejects a bare string, and write each finding to the review ledger as you report it — both are required, not either/or (`agents/senior-engineer.md` §How You Work step 3). Be specific (the file and the **symbol** — or a quoted literal where no symbol exists — a line number only as a hint beside it, per `references/review-rules.md` §Durable References), following the finding form in `agents/senior-engineer.md` §How You Work step 6, group related issues together, and don't fix things yourself. **Findings on vendored / source-of-truth files** (per the CLAUDE.md manifest) — a file listed there is owned upstream, so don't raise findings against its internals; route them to the upstream/source-of-truth owner instead so the copy isn't "fixed" only to be overwritten on the next sync. **Escalate to the user only for a decision that crosses one of the five bright lines in `skills/board/references/escalation-contract.md`, is the sixth route below, or asks for a fact only the user holds (`fact`)** — and escalating means handing it to the **team lead**, who posts it; you have no board channel of your own. A **technical** disagreement with the implementer you cannot settle on evidence is the sixth route — take it to the **team lead** with both positions and the evidence each rests on, declared `teammate-unsettled`. You do not post it yourself. A small addition you would recommend doing in this PR is a finding you report like any other, not a scope question you escalate — scope reaches the user only on the three conditions in `skills/board/references/escalation-contract.md` §The small-addition carve-out. Driving the review to convergence is the team lead's job, so review length is never itself a reason to involve the user. This binds every round, including the first. An improvement to the workflow outside the story you are working is not a finding and not an escalation — it goes to the process improvement notes and nowhere else. What still reaches the team lead is the review you cannot finish — "I cannot complete this review" is a blocker and names what stalls (`skills/board/references/escalation-contract.md` §Workflow improvements are notes).

8. **Re-review after fixes.** After implementers commit fixes (committed in the shared worktree, not yet pushed — you re-review before the team lead pushes): **first establish this round's stance and scope, and report both** (`references/checklist.md` §Review Stance). Run `review-ledger stance --ticket "<TICKET-ID>" --sha "<pinned-sha>"` to compute the stance and delta scope rather than assuming either from the round number — treat whatever it reports as this round's stance; a computed value of `undetermined` reviews adversarially the same as a fired predicate, it is not a third label you branch on alongside adversarial and cleanup (`references/checklist.md` §Review Stance). Then review at that stance and scope: `git log` to see what changed; read the whole passage each hunk sits in, not the changed clause; verify the dispatched fixes landed and the findings they were for are discharged; verify the fixes introduced no regression; read each delta commit no finding cites (`references/checklist.md` §Review Stance, *The cleanup round*). If new issues are found, loop again — a cleanup round's out-of-scope observations come back as routed lines, not findings, as does remediation prose at a `(file, symbol)` an earlier finding was already discharged at, on any round, subject to the exits `references/checklist.md` §Review Stance, *Routed lines* gives from that carve-out.

9. **Approval.** When every item on the checklist passes and the diff is clean: notify the team lead — "Review complete. Approved." The team lead handles pushing the branch and creating the draft PR. Do NOT approve if anything is outstanding. The bar is: **the user finds nothing.** A routed line is not outstanding: it does not by itself justify another round. **A senior may not hold approval on a routed line** — report it alongside the approval instead (`references/checklist.md` §Review Stance, *Routed lines*).

Full checklist: `references/review-rules.md`. Long-form guidance and procedure: read `references/checklist.md` — mandatory before your first run of this skill in a session.
