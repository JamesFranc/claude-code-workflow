# Memory Review

## Overview

Maintain the persistent memory store at end-of-project, the way Process Improvement Notes curates the project's process observations. Memory is meant to be **curated, not append-only** — your operating instructions already say to update stale files and delete wrong ones, but nothing forces that reckoning at a natural boundary. End-of-project is that boundary.

This skill runs in two tiers and is standalone-invocable (like Process Improvement Notes). It operates on **your persistent memory store** — the per-project `memory/` directory and its `MEMORY.md` root index, described in your operating instructions. The index can grow into a tree of index files below that root (§The Index Structure) — read that section before assuming the store is still the flat list your operating instructions describe. **Resolve that directory from your session context; never hardcode its path** (it is keyed to the workspace root, which may differ from the current repo directory).

It maintains a **second store** alongside memory: the user's review-standards file. Spawned agents never read the memory store, so a standard filed only there never reaches the senior engineer — the review-standards file does reach them. Routing guidance to the right store is part of this checkpoint, not a separate errand — see §The Second Store — Review Standards.

**Every node in the index has a size budget, and outgrowing it is a structural signal — not a cue to start deleting.** `MEMORY.md` is loaded into context every session, and past a ceiling it is truncated — entries below the cut silently stop loading, so a memory that fell off the tail is effectively lost even though its file still exists. The exact figure is observed, not documented (§The Index Structure — The trigger), so don't encode it as a hard rule. Watch the mechanism — a node approaching its limit — and when it does, **split that node rather than culling to buy room** (§The Index Structure). Culling keeps its own bounded authority over what is wrong or obsolete; it is never the remedy for a node that has simply got long, because that trades durable knowledge for context and gets more expensive the better the store gets.

## The Index Structure

The index is a tree of no fixed depth: leaves are memory files, and every node above a leaf is an index file that lists one line per entry, each pointing at either a leaf memory or a child index file. **A node may hold both together** — mixed nodes are legal, and necessary: without them, a memory matching no existing child would have nowhere to go, since a node can't mint a new child for it (only a split does that) and, under a strict either/or, couldn't hold it directly either. `MEMORY.md` is the root, and it is the only node that loads every session; everything below it is read on demand as you walk down to the node that owns the subject you're working on.

**Growth is lazy, and that governs everything below.** Depth zero — a flat `MEMORY.md` listing every memory directly — is the default and stays correct for as long as it fits. Structure appears only where a node actually overflowed: most stores never split at all, and a store that has split once has no reason to split anywhere else. One subtree splitting never obliges its siblings to — a category that stays small stays a single node however deep the tree gets elsewhere.

**The trigger.** A node splits when it approaches the ceiling — observed at ~200 lines, the practical figure to measure by reading the file's line count directly (`wc -l` or equivalent); a ~25k-character figure is the context cost that motivates the limit, not what you count. This is checked per node, not once against the root — every node, at every depth, is subject to the same trigger. There is no exact threshold and the ceiling itself is observed rather than specified, so this is a judgement call against a signal. Firing early costs a pointless read hop; firing late costs silently dropped tail entries — lean late. The reference implementation in this workspace's own store split its root once, at 162 of ~200 lines (81% of the ceiling) — that is roughly how late "lean late" means in practice, not the earliest plausible moment.

**Measuring, not estimating.** Judge a node's size by reading the file directly, or counting its lines (`wc -l` or equivalent) — don't estimate from what's visible in your context. Only the root is auto-loaded into context every session, by a mechanism with its own truncation ceiling separate from how you read a file on demand; trusting that automatic copy is what lets an already-over-ceiling root permanently read as "still fine, not truncated" — the exact failure the ceiling exists to prevent. Every other node is not observable at all without an explicit read: nothing auto-loads it, so until you go look, you have no information about its size, not even a stale one.

**A node's contents.** Every entry line in a node — whether it points at a leaf memory or at a child index file, and a node may hold both kinds together (mixed nodes, above) — must carry a hook naming what that entry decides, not merely labelling it: relevance is judged from the line alone, so a vague hook loses everything beneath it, and the deeper the tree the more a bad hook hides. The heading and the one-line description in the template below carry no hook of their own — only the entry lines beneath them do. At depth zero every entry line in the root points at a memory directly; a split replaces the entries it partitioned with child lines, but the node keeps accepting new leaf lines directly for anything that doesn't fit an existing child, which is why a split node is commonly mixed rather than purely child-only.

**The write protocol.** A new memory's pointer goes into the node that owns its subject: descend from the root while exactly one child's hook matches, and write the pointer in the node where the descent stops — a leaf line alongside whatever that node already holds, carrying its own hook naming what it decides (§A node's contents). The descent stops as soon as that's no longer true, whether because no child matches or because more than one does: ambiguity is a stopping condition, not a tie to break, and stopping there puts the memory at the highest node where the ambiguity exists — exactly where a dedupe walk starting from a matching ancestor will still find it. Ambiguous memories accumulating at that node push it toward its own ceiling, which triggers a split there — re-partitioning is what sharpens the hooks that caused the ambiguity in the first place, so hook ambiguity converts into the same split pressure that resolves it. That's a stopping condition, not a guarantee: it depends on noticing that more than one child matches; descending into one anyway when you don't notice is a benign miss, landing the memory a level too deep rather than losing it. A pointer written without a hook is an incomplete write, whichever node it landed in. At depth zero that node is the root itself; deeper in the tree it may already be a split node with children of its own, which is exactly the case mixed nodes exist for (above), so the descent always has somewhere valid to stop and nothing needs to be force-fit into a poorly-matching child. A node gains a new line for a *child* only when a split creates that child — every other new line the write protocol adds is a leaf pointer, and nodes are never hand-created outside a split (below).

**The split.** When a node approaches the ceiling: partition its entries into a small set of obviously distinct groups — few and distinct beats many and overlapping, since a group nobody can tell apart from its neighbour loses both — then write one child index file per group, each carrying a heading, a one-line description, and that group's entries with their own hooks, at a path confirmed not to already exist (placed under `indexes/`, nested one level deeper if the node being split is itself already a child) — a name collision stops the split before the parent is touched, never a silent overwrite — the node stays over its ceiling until the collision is resolved and the next heavy pass retries. Write every child file first; only once all of them exist do you replace the parent's own former entries with exactly one line per new child, each carrying its own hook — in that order, so an interruption between the two steps leaves orphaned child files — caught by the next integrity check's node-reachability clause (below), not otherwise visible — rather than a parent pointing at children that don't yet exist (broken reachability). Only after every write lands does the operation verify (Integrity check, below) — there is nothing to verify before the writes exist. Before overwriting any node — the root above all — note what it held beyond its pointer lines (a preamble, harness-written notes, anything else) and carry that content forward into the node's new form; a split that silently drops non-pointer content is the one irreversible step in this operation, so get it right before the original is gone. Splitting moves no memory: no leaf is renamed, merged, rewritten, or deleted by a split, and cull is never folded into it — a split that also culls has hidden a lossy operation inside a structural one. Splitting the root is what adds a level to the tree; splitting a node six levels down works exactly the same way. This operation is heavy-mode only (§Modes) — it needs the whole-subtree view light mode doesn't take.

**Emptying, the inverse of splitting, and the root is its base case.** When a node is left with no entries — a cull removed its last one, or a Reconcile or Promote relocated its last one to a better-fitting node — delete the node and the line pointing at it — recursively, since removing that line may in turn empty its parent. Whatever emptied the node, the cascade is the same. The recursion stops at the root: the root is never deleted, and an empty root is a legal state. The root has no parent, so the clause that bounds the operation everywhere else — "and the line pointing at it" — constrains nothing there; without this base case the rule reads as deleting `MEMORY.md` itself. An empty root isn't an error to repair, either: it's exactly what a brand-new store looks like before its first capture, and what a fully-culled store looks like after its last. A dead line in an ancestor is exactly the rot the integrity check below exists to catch.

**Emptying is heavy-mode work; light mode never cascades it.** Only heavy mode's walk actually deletes an emptied node and its pointer. Light mode's Reconcile can still relocate a memory's last pointer out of a node — light mode runs Reconcile, just not the cascade — because deleting a node changes the tree's shape, and light mode never restructures it (§Modes). Light mode leaves the empty node in place; the next heavy pass's integrity check catches it (no node is empty except the root, above) and cascades it then.

**Integrity check.** Every leaf is reachable from the root by exactly one path; **every node is reachable from the root**; no pointer dangles; no node is empty **except the root** (its base case, above); every node's lines resolve to a real file. Run this — heavy mode only; light mode never runs the integrity check — after any split, and after any cull or relocation (Reconcile, Promote) that emptied a node during that same heavy-mode walk. A relocation light mode performs is left for the next heavy pass to find and check, not verified in the moment. The node-reachability clause is what makes an orphaned index file detectable — one written but never linked, by an interrupted split or a botched relocation. Leaf reachability alone doesn't cover it: an orphan's own leaves simply aren't on any root path, so every other clause passes over it in silence.

**What the integrity check cannot see.** Whether a memory sits under the *right* subtree is a judgement, not a mechanical property the check above can catch: a memory filed in the wrong node is still reachable from the root by exactly one path, dangles nothing, and passes every clause of the integrity check clean. The same is true of a hook — no clause of the check reads one: a line with no hook at all, or a stale hook left after a Reconcile or Promote that changed what the memory says, passes every clause just as cleanly, and it's the costlier blind spot of the two — a bad hook loses everything beneath it, where a misfiled memory loses one entry. That is why placement is an obligation on Capture, Reconcile, Cull, and Promote (§The Four Operations), and the hook is an obligation on whichever of them writes one — Capture, Reconcile, Promote — never delegated to verification either way: a check that implied it could catch misplacement or a bad hook would be trusted for something it cannot see.

**Not a B-tree in one respect.** This structure does not rebalance: it never redistributes entries between siblings to keep depth even. Uneven depth is deliberate (Growth is lazy, above) — do not "fix" this by adding a rebalancing pass; a redistribution would move memories between nodes for no reader-visible gain. Its cost is accepted, not overlooked: repeated culls can leave a chain of thin, single-entry nodes, each costing a read hop for no gain — a known consequence of not rebalancing, not a defect to patch.

A node's file looks like this, whether it is the root or six levels down — the same procedure produces both:

```markdown
# <Node Title>

<One line describing what this node covers and what it lists — memories, child index files, or both.>

- [Entry Name](path/to/entry.md) — what this entry decides, specific enough to skip
```

The root's version additionally states the write protocol above in its own preamble, so an agent reading the store sees the local rule without needing this skill.

## Input

- **Mode** — `light` or `heavy`.
- **Ticket / epic context** — the ticket ID(s) and summary of the work just completed.
- **Persistent memory store** — the `memory/` files: the leaf memory files, the `MEMORY.md` root index, and whatever index files sit between them once the tree has grown (§The Index Structure).
- **Review standards file** — `<launch-dir>/.claude/review-standards.md`, the second store this skill maintains (§The Second Store — Review Standards). It will not exist until the first standard is recorded; that is normal, not an error.
- **Process-improvement notes** — the project's notes file(s) under `docs/plans/process-improvement/`. Heavy mode reads them in full as source material; the skill locates them itself so a standalone run works.
- **The completed work** — the session and recent git history.

## The Four Operations

Every review applies some subset of these moves to the memory store. These four act on individual memories; maintaining the index tree that finds them — splitting a node, and cleaning up a node any of these operations left empty — is a separate class of move, covered in §The Index Structure.

- **Capture** — a durable fact surfaced by this work that is not yet stored → write a new memory file (one fact per file, with the standard frontmatter) and add its pointer, with a hook naming what it decides, to the node that owns its subject (§The Index Structure — The write protocol).
- **Reconcile** — a memory the work contradicted or made stale → update it to the current truth. If the update changes what the memory is about, its pointer may no longer belong in the node it's currently filed under, and its hook may no longer describe it — move the pointer to the node that fits and rewrite its hook to match what the memory now says, the same way Capture would place and hook a new one (§The Index Structure — The write protocol). Moving a stale hook to a better node relocates the problem instead of fixing it. If relocating it empties the node it moved from: **in heavy mode**, delete that node and its own pointer too, recursively (§The Index Structure — Emptying, the inverse of splitting, and the root is its base case) — the same cascade Cull triggers below; **in light mode**, leave the empty node in place — light mode never restructures the tree, and the next heavy pass will find and cascade it (§The Index Structure — Emptying is heavy-mode work; light mode never cascades it).
- **Cull** — an obsolete, one-off, or wrong memory → delete the file and its pointer, wherever in the tree that pointer lives. If that empties the node it lived in, delete the node and its own pointer too, recursively (§The Index Structure — Emptying, the inverse of splitting). Stay within your existing memory-deletion authority: delete only what is wrong or obsolete, never what is merely old — and never as a way to make room in the index, which is what splitting exists to make unnecessary.
- **Promote** — a `project`/story-scoped memory that proved durable beyond its story → rewrite it as a generalized `feedback`/`reference` fact, dropping the story-specific framing (and re-type it). Generalizing is the move most likely to change what a memory is about — check whether its pointer still belongs in its current node and move it if not, and rewrite its hook either way so it still names what the generalized memory decides, the same as Reconcile, including the same emptying cascade if the move leaves its old node with nothing left in it.

**Decision rule (per memory):**

| Memory state | Action |
|---|---|
| `project` memory whose work shipped, value was single-story | **Cull** |
| `project` memory whose work shipped, encodes a durable lesson | **Promote** → `feedback`/`reference`, generalized |
| `project` memory still in-flight | Keep / **reconcile** to current status |
| `feedback`/`reference`/`user` contradicted by this work | **Reconcile** (or **cull** if wholly wrong) |
| Durable fact from the notes/session, not yet stored | **Capture** |

Before capturing, **dedupe against what already exists** (walk the index tree — the root, plus whichever nodes below it are relevant to the subject, per §The Index Structure — The write protocol — and scan the filenames) — continuous capture may already have written the fact mid-session.

## The Second Store — Review Standards

Not every piece of user guidance belongs in memory. **Spawned agents never read the memory store.** The senior engineer reads the review-standards file — `<launch-dir>/.claude/review-standards.md`, plus a per-repo file read additively where the user made one — and treats every rule in either as a blocking checklist item (`skills/code-review/references/review-rules.md` §User Review Standards). A review standard filed only as a memory is a standard the reviewer will never see.

**Resolving `<launch-dir>`:** the directory Claude was launched in — for a multi-repo workspace the parent that spans the repos, not any single repo's git root. Use your original top-level cwd, **not** a worktree and **not** `git rev-parse --show-toplevel`. Write **exactly one file**. A per-repo `<repo-root>/.claude/review-standards.md` is read additively by the reviewer if the user made one, but is **never ours to author** — creating one scatters conflicting review files across sub-repos.

**The routing test — could a reviewer hold a diff to it?** A review standard reads as a rule a diff either satisfies or violates ("every X must Y", "never approve without Z"). Guidance about how *you* work — process, tooling, escalation, protocol — is not a review standard even when it concerns reviewing; it stays a memory.

| Guidance | Destination |
|---|---|
| A rule a diff can be held to, binding only at review time | **Standards file only** — deliberately not also a memory: every line in the index costs a read hop and needs a hook that earns its place at its node (§The Index Structure), and a rule the reviewer alone ever applies shouldn't make a reader pay that cost for something they never needed there. |
| A rule a diff can be held to, that also binds while you work | **Both** — the standards file so the reviewer enforces it, a memory so you apply it before review. |
| Process, tooling, escalation, or protocol guidance | **Memory only** — per the four operations above. |

**Writing the file:**

1. **Create it when it is absent and there is a standard to record.** `mkdir -p` the `.claude` directory, then write the file led by this header before appending the rule:

   ```markdown
   # Review Standards

   Rules the senior engineer enforces as blocking checklist items on every review.
   Maintained by the memory phase (`workflow:memory-review`).

   ## Rules
   ```

   Creating the file in order to record a real standard is **not** auto-seeding. Absent-with-nothing-to-record is the no-op: never create the file just to have one. A standard need not be stated outright — record one when you can name its **antecedent** *and* a diff can be held to it (the routing table's test, unchanged). An antecedent is something that happened: a preference the user expressed, a correction they made, or a defect this work hit. You may generalise *from* what happened; what you may not do is generalise from what you only reasoned. A conclusion you reached is not itself an antecedent, however sound — a rule with no event behind it is invention, and it is the case to leave out. Judge this yourself rather than asking per rule; when genuinely unsure, leave it out, because a needless rule blocks every future review while a missed one costs a single restatement. The antecedent is the test, not content — it does not go in the entry, which states only what a diff must satisfy.
2. **Sharpen the existing rule first.** The default action for a new standard is to sharpen the existing rule it belongs under; adding a new entry requires stating why no existing rule covers it. An existing rule is still edited or removed only where that sharpening, a prune, or the user's own instruction calls for it.
3. **A standard can only tighten the gate.** A rule may add a blocking requirement; it can never relax, override, waive, or skip a baseline check. The review checklist rejects such a rule at read time — do not author one at write time.
4. **One rule per entry, written as the requirement.** An entry is a single `-` bullet under `## Rules`. State what a diff must satisfy, not the story that produced it. The reviewer reading it months from now has none of this session's context.
5. **The file is capped twice: at 25 entries, counted by `grep -c '^- ' <launch-dir>/.claude/review-standards.md`, and at 25,000 bytes, counted by `wc -c < <launch-dir>/.claude/review-standards.md`.** Entries grow instead of multiplying, so a count under the entry cap says nothing about what the file costs the senior engineer, who reads it in full every review round; the byte figure is the ~25k-character context cost that §The Index Structure — The trigger names for the memory ceiling. `skills/code-review/references/review-rules.md` is capped at 162 entries, enforced by `check-refs`'s `entry-cap` guard (`pnpm lint`); the standards file's two caps are prose-only, since it lives outside every repo and no guard reads it. Crossing a cap is not a warning: the write that would leave the file over either cap does not complete until both counts are within their caps, by tightening an entry's wording, merging entries that state the same standard, or dropping the weakest. Which entries go is your call, never the user's: rank every entry — the one you are adding included — by how much it matters, then merge or drop from the bottom, which may mean the new entry itself does not make it in. Do not ask the user which entries to cut. This file is outside every repo, so no diff records the cut — the archive does. Before writing the file, append every entry that leaves it or never enters it — a dropped entry, each entry a merge or a tightening replaces, and the new entry when it is not added — verbatim to `<launch-dir>/.claude/review-standards.archive.md`, under a heading carrying today's date, each followed by a one-line reason (dropped, merged into which entry, tightened, or not added). Create the archive with a `# Review Standards — Archive` header if it is absent, and never edit or remove what is already in it. For `review-rules.md`, the PR diff is the record.

## Modes

### Light Mode

Called on **every** story close (from Team Cleanup). Keep it fast:

1. **Capture** the durable learnings from *this story* that aren't already stored — except a review standard that binds only at review time, which goes to the standards file in the **Route** step below **instead of** here (§The Second Store — Review Standards). Add the pointer per §The Index Structure — The write protocol: descend while exactly one child's hook matches, and write in the node where the descent stops — light mode never creates a node; new nodes come only from a split, which is heavy-mode work (below). A capture may push the node it lands in — the root included — over its ceiling; leave it there, since light mode never splits either; the next heavy pass's walk will find and split it.
2. **Reconcile** any memory this story plainly contradicted or made stale. If this relocates a memory's last pointer out of a node, leave that node in place — light mode never restructures the tree (§The Index Structure — Emptying is heavy-mode work; light mode never cascades it); the next heavy pass's integrity check will find and cascade it.
3. **Route** any review standard this story surfaced to `<launch-dir>/.claude/review-standards.md`, creating the file if it is absent, following that section's numbered write procedure (§The Second Store — Review Standards). This is not a sweep — it covers what this story surfaced, and a story that surfaced none is a clean no-op. A standard binding **only** at review time goes to the standards file *instead of* a memory; one that also binds while you work goes to both — per the routing table in §The Second Store.

That's all. Do **not** sweep the whole store, and do **not** cull or promote in light mode — those are heavy-mode moves. Splitting a node is a heavy-mode move too (§The Index Structure) — light mode writes within whatever tree shape it finds, and never restructures it.

### Heavy Mode

Called when the whole unit of work finishes (last story of an epic, or a standalone story), and on a standalone "review my memories" request. This is the full consolidation:

1. **Read the project's process-improvement notes in full** — they are the record of what happened and the richest source for capture and promotion. Nothing checks them before you do: they are gitignored and outside every gate, CI run and diff review (`skills/code-review/references/checklist.md` §The artifacts no gate reads), so a memory captured or promoted out of them carries whatever went in, and this read is the only check a claim gets before it outlives the ticket.
2. **Walk every memory in the store** and apply the four operations per the decision rule above.
3. **Backfill the review-standards file from the store — after the walk, not before.** A memory the walk culled must not be promoted at all, and one it reconciled or promoted must reach the file as the walk left it, not as it stood before; running earlier would write the stale version and turn a wrong memory into a blocking review rule. The tests in §The Second Store apply to memories already written, not only to what this session surfaced. A memory that clears them belongs in `<launch-dir>/.claude/review-standards.md` — write it there following that section's numbered write procedure, creating the file if absent. Heavy mode runs more than once, and a memory kept because it also binds while you work is re-read on every run, so an unchecked write re-appends the same rule each time. Cull the memory only when it binds *nowhere but* review — once the rule lives in the standards file, a memory that existed solely to carry it **is** obsolete, which is what makes this a legitimate cull under §The Four Operations rather than deleting something merely old. When it also binds while you work, keep both. This is how a store that accumulated review rules before the standards file existed gets them in front of the reviewer, instead of waiting for the user to restate each one.
4. **Log each cull and each promotion with a one-line rationale** (which memory, which action, why). Destructive and re-typing moves are never silent — a standalone run must be reviewable. If a cull's rationale isn't clear-cut obsolete/wrong, downgrade it to reconcile rather than delete.
5. **Reconcile the index tree, then check every node against the trigger.** End by making the tree consistent with the files, per §The Index Structure — Integrity check: every leaf reachable from the root by exactly one path, every node reachable from the root, no pointer dangling, no node empty except the root — a cull or a relocation (Reconcile, Promote) that emptied a node needs its cascade applied here, whether it happened earlier in this walk or was left behind by an earlier light-mode pass that never cascades (§The Index Structure — Emptying is heavy-mode work; light mode never cascades it). Then walk the tree itself, node by node, root included, and weigh each one's size against the ceiling by reading the file directly, never from what's visible in context (§The Index Structure — Measuring, not estimating). Split any node at or near the ceiling, per §The Index Structure — The split. Do **not** cull or merge memories to buy room — splitting is what makes room, and a store big enough to hit the ceiling is a store worth keeping whole. The line-count figure is a soft reference, not a hard limit (§The Index Structure — The trigger).

## Key Rules

- **Curate, not append** — the point of the checkpoint is to reconcile, cull, and promote, not only to add.
- **Review standards are a second store** — guidance a reviewer could hold a diff to goes to `<launch-dir>/.claude/review-standards.md`. Spawned agents never read the memory store, so a review rule filed only as a memory never reaches the senior engineer.
- **Create to record, never to seed** — creating the standards file to write a real standard is not auto-seeding; creating it empty, or filling it with invented rules, is. A standard need not be stated outright: record one when you can name its antecedent — something that happened: a preference the user expressed, a correction they made, or a defect this work hit, never a conclusion you reached — *and* a diff can be held to it. Judge it yourself rather than asking per rule; when unsure, leave it out. Never author a per-repo `<repo-root>/.claude/review-standards.md`.
- **Standards are additive only** — a rule may add a blocking requirement, never relax, waive, or skip a baseline check.
- **Light stays light** — capture, obvious-staleness, and routing the standards this story surfaced; the full walk, the cull/promote pass, the store-wide backfill, and any index restructuring (splitting a node) are heavy-only.
- **Cull is bounded and logged** — only wrong/obsolete, each with a rationale; ambiguous cases are reconciled, not deleted. A cull that empties a node cascades up the tree (§The Index Structure — Emptying, the inverse of splitting).
- **Promotion drops story framing** — a promoted memory reads as a permanent general fact and is re-typed to `feedback`/`reference`; check whether its pointer still belongs in its current node (§The Four Operations).
- **Dedupe before capturing** — walk the index tree from the root into whichever nodes are relevant, and check the filenames, so continuous capture isn't duplicated.
- **Index integrity** — heavy mode leaves every leaf reachable from the root by exactly one path, every node reachable from the root, no dangling pointers, and no empty node except the root, whose empty state is legal (§The Index Structure — Integrity check).
- **A node's load budget is measured, not estimated, and the fix is structural** — the root is auto-loaded into context every session and truncated there past a ceiling; judge every node's size from the file on disk, not from what's visible in context (§The Index Structure — Measuring, not estimating). A node approaching the ceiling is a trigger to split it, never to cull; culling to make room spends durable knowledge on context.
- **Grow lazily, and only in heavy mode** — depth zero is the default and stays right until a node nears the ceiling. Structure below the root is overhead where nothing has overflowed; lean late rather than early.
- **Resolve the store from context** — reference the memory store and its `MEMORY.md` abstractly; never write a hardcoded memory path into a memory file or here.
- **Standalone-usable** — runnable directly to review a project's memories after the fact; it finds the process-improvement notes itself.
