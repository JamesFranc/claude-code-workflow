# Restart jobs

Background jobs and teammates do **not** survive a restart — a process exit, a crash, or `claude --resume`. After one the session looks alive, but its background watchers and any teammates are gone, silently. This command brings the background jobs back and re-establishes the team.

You're most likely running this because the session just restarted. With that in mind:

1. **Reassess dashboard session state before relaunching anything.** The local node registry survives a restart, but a leaf in it can name a node the board has since ended or closed — and the wake mod, which restarts with the session and is already running, acts on whatever the registry names: its board check polls every node in the registry and its heartbeat beats every leaf in it. Repair a stale leaf first, so that nothing you relaunch in step 2 starts against it.
   - Run `dashboard session status` and read **both** sides. Never trust local state alone: the registry survives a restart and a leaf in it may name a node the board has ended or closed.
   - Identify the node you should be updating, from the work in flight (the ticket, the phase) — not from whatever the registry happens to say.
   - State plainly which session you are updating and why.
   - **When local and board agree:** say so and change nothing.
   - **When a registry leaf names a node the board reports `ended` or `closed`, or a node the board does not have at all**, which kind of node it is decides the recovery — a dead root and a dead non-root leaf are not the same case. Say what changed, either way:
     - **dead ROOT** (registry root, `parentId === null`): leave any live child leaves first — `leave --root` refuses while the root still has children — then release the root itself with `dashboard session leave --root`, or `dashboard session repair --forget "<internal-node-id>"` if `leave` cannot. Follow with a two-command mint, not a bare keyless `--phase "<phase>" --title` on one line: `dashboard session enter --phase dispatch --title "<ticket summary>"` mints and names a new top-level board session (FLOW-190), then `dashboard session enter --phase "<phase>"` advances to the working phase. A one-line keyless `--title` enter would be refused by the guard hook at a blocked phase (`implementation`/`review`/`pr`/`pr-feedback`/`cleanup`), and adding `--retitle` to force it through would reintroduce the exact silent-rename hazard Team Dispatch's own entry-point block was fixed to avoid. No `-resumed` key, no `--parent-key`. Then register its ticket link — a freshly minted node carries none yet. This recovery path has no Jira call in scope, so fetch the ticket's canonical browse URL first with `getJiraIssue` (the `webUrl` field) — never a hardcoded host: `dashboard link add --kind ticket --label "<TICKET-ID>" --url "<jira-url>" --root` — the node just minted is the root itself, since every live child leaf was released above before this mint ran (`skills/board/references/dashboard-protocol.md` §1).
     - **dead NON-ROOT leaf**: repair local state with explicit ids — `dashboard session repair --forget "<dead-node-id>"` — then re-establish the work under a **new key**, never the dead node's own key: `dashboard session enter --phase "<phase>" --key "<TICKET-ID>-resumed" --title "<ticket summary>"`. A new key composes a new external id, so a fresh node is created and the dead one stays dead — and a fresh node needs `--title` to name it, the same B4 rule Team Dispatch's own blocks carry. Then register its ticket link the same way — fetch the `webUrl` with `getJiraIssue` first, same as the dead-ROOT case above: `dashboard link add --kind ticket --label "<TICKET-ID>" --url "<jira-url>" --key "<TICKET-ID>-resumed"`. Nothing further is needed to propagate this key: every downstream site resolves it with `dashboard session key --ticket "<TICKET-ID>"`, which returns the resumed key from this session's registry (`skills/board/references/dashboard-protocol.md` §1, *The ticket node key*).
   - **Mid-epic with an ended or closed epic session:** the same repair applies, but the epic root is dead too, so a keyed enter for the resumed story has no live root to parent onto and fails with `no live parent session with that external id`. Forget the dead nodes, then mint a fresh keyless root first (the same two-command form as the dead-ROOT case above) and register the **epic's** ticket link on it. Only then enter the resumed story: `dashboard session enter --phase "<phase>" --key "<TICKET-ID>-resumed" --title "<story summary>"` — parented onto the root just minted — and register the **story's** own link on that node; a board node carries exactly one live `kind:ticket` link, its own (`skills/board/references/dashboard-protocol.md` §1). This mints a fresh node under a key used for the first time this session, so it needs `--title` to name it, the same rule as the dead-NON-ROOT-leaf case above. If `<TICKET-ID>-resumed` is itself already taken and ended, keep going — `-resumed-2`, and so on. If it's already taken and **active** (you're resuming a second time in the same raw session), re-enter that node instead of minting another — and omit `--title` on that re-enter: the node already has one, and a differing `--title` throws. **In-flight code — worktree, branch, uncommitted work — is never touched.**
   - Never re-enter a node the board says is `ended` expecting it to stay ended: **re-registering the same external id reactivates it** (measured 2026-07-09). If you deliberately need to revive one, re-run its `link add` too — a reactivated node is exactly a re-entered ticket-level node under the dashboard-protocol invariant. This is a keyed node being revived, and the mid-epic case directly above is precisely where multiple live leaves exist — omitting `--key` here is refused by `resolveLinkAddTarget`'s own keyless check first, so pass `--key` regardless of which message an omission would actually surface. Fetch its `webUrl` with `getJiraIssue` first, same as the recovery cases above: `dashboard link add --kind ticket --label "<TICKET-ID>" --url "<jira-url>" --key "<TICKET-ID>"` (or `<TICKET-ID>-resumed`, matching whichever node was revived). Then dispose of the ticket node you are **not** keeping — `dashboard session leave --key "<the other one>"`, or `dashboard session repair --forget "<its internal id>"` if `leave` cannot — so exactly one live node matches this ticket. Two live nodes for one ticket is a state `dashboard session key` refuses to resolve (`skills/board/references/dashboard-protocol.md` §1, *The ticket node key*), and every downstream re-enter site will error until it is resolved.
   - **With no ticket**, skip every ticket `link add` and `getJiraIssue` fetch above — dead ROOT, dead NON-ROOT leaf, mid-epic and the revival; the `enter` and key steps are unchanged.
   - Use `--dry-run` first if you want to show the writes before making them.

2. **Restart the background jobs you had running.** Look back over this session — the conversation, the process-improvement notes, open PRs — and relaunch whatever long-running background jobs were active before the restart. The usual ones:
   - **PR watch** — nothing to relaunch: a PR registered with `pr-monitor` is on disk, and the wake mod restarts with the session and polls it. **CodeRabbit throttle durability:** a cooloff re-request scheduled before the restart is lost with the session, and a still-present rate-limit banner is **not** re-emitted (the emission is transition-only, by design — that is also what keeps an ordinary restart from re-reporting). So for any open draft PR from this session, check the PR directly — `gh pr view "<n>" --repo "<owner/repo>" --json comments,reviews` — and if CodeRabbit's most recent status is a rate-limit banner or a refused re-request (`Action not completed` with `Review rate limited`) with no review after it, re-establish the pending re-request per the PR Lifecycle `CODERABBIT_RATE_LIMITED` handler (`workflow:pr-lifecycle`). Follow that handler rather than a summary of it: the cooloff, the choice between `review` and `full review`, the re-request and the recording of the comment's id are all steps it states, and a re-request posted without that last step wakes you on your own words.
   - **Anything else** you had launched in the background — other watchers, pollers, or `/loop`-style jobs. Relaunch a watcher with `timeout: 2147483647` (`skills/workflow-guide/references/background-watchers.md`).

   If you suspect a watcher is already live, check for the process before relaunching — do not start a second one to be safe.

3. **Re-establish the team if a story is in flight — in this turn.** A restart terminates every teammate — implementers, the senior engineer — even though their config may linger, so never assume they're still there. A story is in flight from the moment Team Dispatch spins up its team until Team Cleanup runs for it; the team stays alive through implementation, senior review, and the whole PR Lifecycle wait (`skills/team-dispatch/SKILL.md`, the PR Lifecycle step). For a story in flight, re-spawn the team via the Team Dispatch skill (`workflow:team-dispatch`) — its spin-up step, pane check included — as the next action of this same turn: the implementer(s) always, and a senior only when a review round was open, per that skill's per-round senior spawn. Do not end the turn having described the respawn, and do not wait for the user to approve it — restoring the team is a process step, not a user decision, exactly as spinning it up was. Put the work the restart interrupted into the replacement's spawn prompt as its assignment — the commits that landed since the last report, the gates not yet recorded at the current HEAD, and the findings still open on the ledger from a round `review-ledger show` reports complete, never one still in flight. With no story in flight, say so in one line and move on.

If nothing was running — a fresh session, or no restart actually happened — say so and move on.
